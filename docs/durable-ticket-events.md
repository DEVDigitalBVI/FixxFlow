# Durable ticket events — Stage 3

Stage 3 adds database event capture and a durable delivery protocol. It adds no
worker, scheduling, automation execution, action commands, dry run or UI. Stage 1
models/registries/validation and Stage 2 persistence/security remain unchanged.

## Migration and schema

`supabase/migrations/20261001020338_durable_domain_events.sql` introduces:

- `private.domain_events`: immutable event ID, organization, schema version, type,
  entity identity/revision, actor/provenance, timestamp, allowlisted before/after
  snapshots, changed-field names, correlation/causation/root/depth, and a reserved
  nullable automation execution identifier. Unique identity is
  `(organization_id, entity_type, entity_id, entity_version, event_type)`.
- `private.domain_event_deliveries`: event/organization/consumer, pending/leased/
  acknowledged/dead state, attempts, availability, lease token/times, completion,
  safe error code and timestamps. `(organization_id, event_id, consumer)` is unique.
  A composite foreign key prevents a delivery from referring to another tenant's
  event. Root/cause references also use composite tenant keys.
- `public.tickets.revision`: server-owned bigint, bounded to JavaScript's safe
  integer range. Existing rows start at 1 without synthetic events, timestamp
  changes or audit entries.

Indexes support ready deliveries by consumer/availability/ID, entity revision
lookup, tenant correlation lookup, and causal/root references. Events have no FK
to tickets or actor memberships: later ticket/member changes cannot alter their
snapshots. The organization FK retains infrastructure history rather than silently
cascading it away. An explicit retention policy is a later concern.

Both private tables enable RLS with no direct-access policies. All direct table
permissions are revoked from anon, authenticated and service_role. Administrators
cannot enumerate or write the outbox. Existing ticket RLS, MFA, column grants and
composite tenant foreign keys remain the authorization boundary for mutations.

## Transactional capture and revision

`tickets_z_domain_revision` calls `private.prepare_ticket_revision()` after the
existing BEFORE triggers by PostgreSQL's alphabetical trigger ordering. Employee
update restrictions inspect the caller's original update before revision changes;
routing, resolution/closing preparation and SLA preparation retain their existing
functions and order. `tickets_domain_events` calls
`private.capture_ticket_domain_events()` AFTER the completed row mutation.

Revision starts at 1 and increments once if final title, description, requester,
technician, team, classification, priority, status, location, due date, first
response, resolution/closing times, SLA targets or routing mode changes. Pure
`updated_at` churn and no-op updates do not advance it. Client revision writes
have no grants; privileged attempts are also overwritten by the revision trigger.
Some system-only changes can advance the revision without a V1 event. This is
deliberate: later stale-state checks should notice relevant state changes even
when no V1 trigger represents them.

Capture covers ordinary INSERT/UPDATE, multi-row bulk updates, the existing
`create_equipment_ticket` and `convert_chat_to_ticket` RPCs, employee reopening,
and the first-response update generated by a public staff reply. No application
write path or UI publisher is added. Existing routing history, ticket activity,
audit and notifications still run independently.

The ticket mutation, event insert and initial delivery insert commit or roll back
together. A publishing/delivery failure aborts the mutation; errors are not
swallowed. Event capture compares OLD/NEW independently and does not consume the
existing `ticket_activity` elsif chain.

## Exact V1 event semantics

| Event | When emitted |
| --- | --- |
| `ticket.created` | Every successful insert, after routing/SLA preparation. This is the only insertion event, including initially assigned or terminal tickets. |
| `ticket.status_changed` | Any actual status transition, including reopening and resolved-to-closed. |
| `ticket.priority_changed` | Any actual priority change. |
| `ticket.assigned` | A technician or team changes to a non-null value. One event covers simultaneous positive assignment changes. |
| `ticket.resolved` | Entry from a nonterminal status into resolved **or closed**, matching Stage 1. Moving between resolved and closed does not emit another resolved event. |
| `ticket.updated` | Title, description, requester, category, subcategory, location, due date or first response changes, or a technician/team is cleared. |

Pure status, priority and positive-assignment changes do not also emit a generic
updated event. Mixed changes can emit several specialized events plus updated
when it has its own qualifying change. Each event contains the complete set of
changed allowlisted business field names for that mutation. Description changes
are represented only by the `description` marker, never its contents.

Snapshots contain exactly: `title`, `priority`, `status`, `category_id`,
`subcategory_id`, `assigned_technician_id`, `team_id`, `requester_id`,
`requester_department_id`, `location_id`, `due_at`, `first_response_at`.
Requester department is looked up through the same-tenant profile at mutation
time, for each snapshot's requester. Later profile edits do not rewrite events.
Department edits alone do not mutate tickets or publish ticket events. Message
bodies, descriptions, emails, file paths, credentials and complete database rows
are never copied into snapshots. Ticket subjects are retained because Stage 1
supports conditions on them.

`private.ticket_event_snapshot()` is the ticket adapter.
`private.publish_domain_event()` is the generic, private publisher; it atomically
inserts an event and its initial `automation` delivery. A repeated identical
entity/revision/type publication returns the existing event; conflicting payloads
fail. No client or service RPC can invoke this publisher directly.
`private.domain_event_envelope()` serializes the established Stage 1 `DomainEvent`
without adding database-only fields.

## Provenance and correlation

Ordinary events use the authenticated member and check existing active membership
and assurance helpers. Service operations and actorless database maintenance are
marked `system` with a null actor ID. Stage 3 never invents an automation actor or
execution ID; those require the later trusted execution runtime.

Each ticket mutation gets a fresh correlation UUID shared by its sibling events.
Independent root events have depth 0, null causation and `rootEventId=id`, as the
Stage 1 contract requires. They share correlation but remain separate roots.

For future trusted mutation RPCs, `private.domain_event_cause()` recognizes
transaction-local `app.domain_event_delivery` and `app.domain_event_lease` only
when the actual database request role is `service_role`. It locks and checks the
persisted delivery, token, target organization, leased state and current expiry.
Normal authenticated GUC/header attempts confer no provenance. Missing/stale or
cross-tenant service context aborts the mutation rather than silently losing its
chain. A valid parent supplies its persisted correlation/root and depth+1.

This is a database-internal protocol, not a public context-setting RPC. A future
command must set and restore this context within the same database transaction;
setting it in a separate HTTP request would not work. The originating event and
the new entity may differ, provided their tenant matches. Full execution-chain
recursion suppression is intentionally deferred.

## Delivery protocol

Public RPCs, with corresponding private checked definer implementations:

- `claim_domain_events(batch_size=20, lease_seconds=120, consumer_name='automation')`
  returns delivery ID, opaque lease token, expiry, attempt number and the generic
  event envelope. Batch range is 1–100; lease range is 30–900 seconds. V1 has one
  registered consumer, automation. No caller-supplied organization is accepted.
- `finish_domain_event_delivery(delivery_id, token, outcome, failure_code=null)`
  returns whether this acknowledgement was accepted. Outcomes are acknowledged,
  retry, or failed. Errors use only `transient_failure`, `invalid_event`,
  `unsupported_event`, or `permanent_failure`; free-form exception/provider text
  is rejected.

Both RPCs grant EXECUTE only to service_role and independently check the database
request role. Context and tenant identity come from persisted delivery/event
records. Private publishing, snapshots and provenance helpers have no service
EXECUTE grant. Security definers have empty search paths and qualified relations.

Claim uses `FOR UPDATE SKIP LOCKED`, stable availability/ID ordering and a fresh
token for every attempt. Availability equals expiry while leased, allowing an
expired delivery to be reclaimed. Old/incorrect tokens and expired lease
acknowledgements fail; expiry is checked after acquiring the acknowledgement lock.
Matching repeated acknowledgements are idempotent without extending retry time.

Retries wait 30 seconds multiplied by 2 per previous attempt, capped at one hour.
There are at most eight claims. A final retry or expired eighth lease becomes
dead; expiry exhaustion records `retry_exhausted`. Explicit failed outcomes become
dead immediately. Terminal records are retained; there is no automatic replay or
purge. A batch consisting of expired exhausted deliveries can return no leases
after marking those records dead; the future poller must keep polling normally.

This is **at-least-once delivery**, not exactly-once action execution. Token
fencing prevents stale acknowledgement, but a crashed process could have performed
work before acknowledgement. Later execution/action idempotency remains required.

## Stage 4 handoff

- Keep the envelope and delivery protocol independent of polling frequency or
  future lower-latency transport. Minute scheduling is not introduced here.
- Decide how to handle the backlog accumulated before a worker exists. Enabling
  a new rule must not accidentally replay old events; use an explicit enablement/
  event-time policy when selecting immutable rule versions.
- Multiple meaningful sibling events share one entity revision. Preserve their
  distinct trigger identities and use correlation/causation for chain protection.
- Later actions need both execution/step idempotency and current ticket revision
  checks. Delivery acknowledgement alone does not prove exactly-once effects.
- Profile department changes are external to ticket revision. Evaluate the
  captured event-time department, and make any live-data preconditions explicit.
- Future trusted mutation RPCs must establish lease context transactionally and
  restore it before unrelated work. Add verified automation execution provenance
  when those execution records exist; do not trust an arbitrary execution ID.
- Direct service ticket UPDATEs lack the existing worker-helper grant in the
  migration test environment. Separately, `can_work_tickets()` returns NULL for
  absent membership, so the employee guard's `IF NOT ...` does not reject
  actorless owner/definer writes. This existing behavior is preserved and tested;
  ordinary ticket RLS still protects clients. Later automation mutation commands
  must explicitly verify execution and tenant authorization, rather than rely on
  this guard alone. Do not fabricate a member identity or disable triggers.
  Stage 3's service causation tests use creation; trusted maintenance updates are
  captured with system provenance.
- Queue data is retained and accumulates until later consumption/retention work.
  Define monitoring, dead-letter recovery and retention before production rollout.

No Stage 4 implementation is included.
